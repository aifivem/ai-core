# Admin panel host (ai-core server)

ai-core hosts the one admin panel; it never stores or saves another script's data. How a script adds its panel: `.claude/rules/admin-panel.md` in the server repo.

## Decisions

- Every script's `AdminPanel` (lib) registers with the `RegisterAdminPanel` export at start and answers `AdminPanelSnapshot` / `AdminPanelApply` exports; ai-core asks each started one for its snapshot when an admin opens the panel and forwards each edit to the script that owns the file. Exports stay synchronous (validation and the in-memory write are synchronous; the file write is debounced in the script).
- Admin check on every call: ACE `ai.admin` (`permission.cfg`: `add_ace group.admin ai.admin allow`); 30 writes per 10 s per admin; successful edits are logged on ai-core's `admin` log channel.
- Admins with the panel open get every change as a delta (`ai-core:admin:delta`), whoever made it; the panel applies its own edits at once and puts the old value back with the error when the script refuses.
- The panel opens with F10 (keybind `aicore_admin`, its default set in the Keybinds tab) or `/aiadmin` (server `addCommand`, admins only, sends `ai-core:admin:show`), only while a character is loaded; F10 does nothing for non-admins, `/aiadmin` answers them "not allowed".
- Commands tab: the `commands` file is `memory: true` (never saved), one row per command keyed by its name: lib `addCommand` commands as their resources announce them (`commands.ts`, dropped on resource stop) and every other `GetRegisteredCommands()` entry with a resource as plain ("Not declared" permission), re-read when the panel opens and 1 s after resources start or stop. Shown as a read-only `table` tab.
- Keybinds tab: `data/keybinds.json` (`sync: "all"`, key = keybind name) holds each keybind's script, description, default and device plus the owner's `key`. Keybinds exist only on clients: the admin's client sends the ones it knows with the open callback and new or changed ones are committed (the owner's key is kept). A key is checked against the device's key names (`keybinds.ts`). A changed key reaches every client as a delta and applies at once (the lib maps `+<name>_<newkey>`, the old mapping stops acting).
- Principals in an `addCommand` `restricted` list (`group.admin`) get `command.<name>` through `add_ace` (taken back with `remove_ace` when the resource stops); without `command.add_ace` / `command.remove_ace` for `resource.ai-core` in `permission.cfg` ai-core warns once and such commands work only for players with `command.<name>`.
- The panel opens on a dashboard (every script as a card, a search over scripts, tabs and setting labels, other scripts' panels); the sidebar shows only the open script's tabs and folds the others, with a filter on top.
- The open answer (`AdminOpenData`) carries the snapshots, the lookup lists (`lookups.ts`: the active inventory's items, ai-core's jobs, gangs and account types, the started resources, read at open), the other scripts' panels (`external.ts`) the outdated scripts (`../versions.ts`, shown at the top of the dashboard) and the script recommendations (`../recommendations/`, later changes as `ai-core:admin:recommendation` deltas). The lib validates lookup values through the `GetLookupValues` export (cached 2 s per list).
- Other scripts' own settings screens (`external.ts`) come from the owner's list (Other panels tab, `data/externalPanels.json`), `ai_admin_label` + `ai_admin_command` / `ai_admin_url` (+ `ai_admin_icon`, `ai_admin_description`) lines in any fxmanifest, and the `RegisterExternalPanel` export. A command closes ai-core's panel and runs on the admin's client; a url (https only) shows as an iframe inside the panel. A script's normal NUI page cannot be embedded that way (it never gets its own Lua's messages inside the iframe): use its command.
- ai-core's own content (settings, spawn points, job rules, jobs, gangs, accounts) is one more panel (`schema.ts`); jobs and gangs created there get their shared accounts and duty count at once (`server/index.ts`).

## Players section (`players/`)

- Not a schema panel: its own route (`/admin/players`), its own callbacks, built for millions of stored characters. Contract `resource/common/adminPlayers.ts`: one admin-only `onClientCallback` per action (`ai-core:adminPlayers:<action>`, `isAdmin()` guard, args parser, 30 per 10 s), the admin's client relays only listed actions (`client/adminPlayers.ts`).
- Snapshot + delta: `online` subscribes the admin to the list and answers `{ ok }`; the rows follow as latent `rows` events of at most 500 rows (~60 KB), and rows that change are collected and sent once per second the same way (a bigger burst spreads over the next seconds). Latent events can arrive out of order, so every `rows` message carries a revision and the NUI applies a row or removal only when it is newer than the last one it applied for that server id (bench `bench/adminPlayers.bench.ts`); `open` answers one character's `CharacterView` and subscribes to it (one character per admin); `close` ("char" / "all") and `playerDropped` unsubscribe. Changes of loaded characters come from ai-core's own local events (money, jobs, duty, gangs, load / unload) plus `Player.setMeta` / `setInfo`; offline edits push from their mutators (`offline.ts`). Every action answers `{ ok, error? }`.
- Search (`search.ts`): a name (one word: first- or last-name prefix; two words: first + last prefix), a citizen id or a bare number (citizen id, fivem, discord), a 40-hex license, or `fivem:` / `license:` / `discord:`. Names page by keyset on the id (newest first, 25 per page), identifiers answer at most 50 characters. Indexes `search_first` / `search_last` (`deleted_at, name, other name`) and `license` / `discord` on users are in `sql/main.sql` and added once to older databases by `indexes.ts` (in place, lock free). Numbers: the `aicore-fivem` skill's `references/scale.md` (`bench/playerSearch.ts`).
- A loaded character is edited through its `Player` (wallet, job and gang sets, `setMeta`, `setInfo`); a stored one through `offline.ts` with the same rules, while `claims` (player registry) holds it: a character cannot load while an admin edits it offline, and an offline edit is refused while it loads or saves on unload. Money always goes through `Account` (offline: `loadAccounts` + `change` / `set` + `idle`), so the balance delta and the ledger row (reason typed by the admin, actor `admin fivem:<id>`) are written like every other change.
- Online only: duty, kick, revive (ai-core's medical layer: revive, else heal), items (inventory layer), open inventory (the panel closes). Offline only: the sex (the ped model follows it) and delete (soft delete, `deleted_at`). Go to reads the ped or the stored position; Bring teleports a loaded player (`ai-core:client:adminTeleport`, lib `player.teleport`) or moves a stored character's spawn position.
- Every successful action is logged on the `admin` channel with the admin as source and the character's player as target.

## Pitfalls

- Schema panels are not built for scale yet (the Players section is): opening the panel sends every script's whole data snapshot and the panel holds it all; a records file with 100k entries needs server-side paging and search before such a script uses the panel.

- A deleted job or gang is not removed from characters who hold it; they keep the membership until it is changed.
- The pay account select lists the account types that existed at start; a new account type shows after a restart.
- Keybind records of removed scripts stay in `data/keybinds.json` (nothing prunes them).
- A name changed in the Players section reaches the owner's client at once, but scripts that copied it (bridge `charinfo`, ESX names) see it after the character loads again.
- Restarting ai-chat drops the lib's command suggestions on clients until a character loads again (the lib keeps what it sent per player).
