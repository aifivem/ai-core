# vRP bridge (`bridge/vrp/`)

ai-core `provide`s `vrp` and answers vRP 1 (1.0, 0.5 call style), vRP 2 and vRP 3 together. Coverage and limits: `docs/compat/vrp.md`.

## Layout

- Root files scripts include or `module()`: `lib/` (utils, Proxy, Tunnel, Tools, IDManager, Luaoop, htmlEntities, Luang, Lang, Debug stub), `cfg/` (base, modules, client, gui, lang/en), `vRPShared.lua`, `client/vRP.lua`; all in `fxFiles`. `lib/utils.lua` is also an ai-core script on both sides (before every `bridge/vrp/` file), so ai-core's runtime has `module`, `async`, `class`, `Proxy` / `Tunnel` through `module`. Our `module("vrp", p)` reads `ai-core` directly.
- Copies of vRP files (Luaoop, IDManager, htmlEntities, Luang, Lang, Tools, vRPShared, client/vRP, cfg/lang/en) stay unchanged apart from a header line and `---@diagnostic disable`; Proxy, Tunnel, utils, Debug and the other `cfg/` files are ours.
- `server/interface.lua`: `BridgeVRP` (`proxy`, `tunnel`, `client`, `userId`, `sourceOf`, `await`), the v1 id functions, vRP 1's player events; `server/data.lua`: `data.get/set`, `query`. `client/interface.lua`: `BridgeVRPClient` (`tvRP`, `server`).
- `v1/`: the vRP 1 API. Server `v1/server/`: `base.lua` (mapping `BridgeVRP.config()` / `onConfig(fn)`, helpers `BridgeVRP.mirror(user_id)` -> mirror, source, `isCallable`, `call`, `caller`, `warnOnce`), `users.lua` (users, data tables), `data.lua` (UData / SData, DB), `money.lua`, `group_match.lua` (what a character holds: `BridgeVRP.holdsJob`, `hasGroupOf`, `groupSet`...), `groups.lua`, `permissions.lua`, `group_events.lua`, `items.lua` (item ids, `BridgeVRP.itemOf(idname)`, script items), `inventory.lua` (inventory, chests), `weapons.lua`, `identity.lua` (identity, survival), `map.lua` (areas); client `v1/client/`: `base.lua`, `map.lua` (blips, markers, areas), `state.lua` (health, coma, cuffs, vehicles), `customization.lua` (weapons, customization). vRP 2 calls these through `BridgeVRP.proxy.<name>`.
- JS side: `resource/server/vrp/` (key-value store, `VrpQuery`, `data/vrp.json` mapping), `resource/server/characters/info.ts` (`GetCharacterInfo`).

## Adding a function

- v1 server API: `function BridgeVRP.proxy.<name>(...)` in a new file `bridge/vrp/v1/server/<topic>.lua` listed in `fxServerScripts` after `bridge/vrp/server/data.lua` (before the GUI files). The proxy looks members up at call time, so nothing else is registered. Return values the way vRP does (several returns, nil for "none").
- Client API: `function BridgeVRPClient.tvRP.<name>(...)` (`bridge/vrp/v1/client/<topic>.lua`), reachable from the server as `vRPclient.<name>(source, ...)` and from client scripts as `vRP.<name>(...)`.
- A server function clients may call: `BridgeVRP.tunnel.<name>`; it runs behind `Bridge.allow` (30 per 10 s per player, shared with the QB / ESX callbacks) and must validate every argument and key state by `source`. Never a money or item function.
- Calling a client from the bridge: `BridgeVRP.client.<name>(source, ...)` (waits; `_<name>` does not; `-1` = everyone, never answered).
- Functions another resource passes in (0.5 callbacks inside the args, menu choices) arrive as callable tables: `BridgeVRP.isCallable` / `BridgeVRP.call` on the server, `BridgeUI.isCallable` / `BridgeUI.call` on the client.
- Weapons are inventory items (owner decision): `lib/Tunnel.lua` routes a server script's `vRPclient.getWeapons / giveWeapons / replaceWeapons(source, ...)` (`Tunnel.serverMembers`) to the server proxy functions of the same name; the client `tvRP.giveWeapons` refuses. Add a member there only for a client function whose effect the server must own.
- v1 ids: `user_id` = character id; answer nil / 0 / false / `{}` for a character that is not loaded (vRP 1 reads online data tables only), except data that lives in the DB (UData, `getUserIdentity`). Money amounts are floored, negative refused; inventory weights are grams in ai-core, kg in vRP.
- A handler that waits (`BridgeVRP.data`, `BridgeVRP.query`, a tunnel call, a prompt) makes the caller wait in a thread, as in vRP; a handler that only reads the mirror answers synchronously (0.5 scripts call without a thread).

## GUI (`BridgeVRP.ui`, `bridge/vrp/server/gui/` + `client/gui/`)

Everything is drawn by ai-lib's menu, input dialog and notification cards through `BridgeUI` (`bridge/core/client/`: `ui.lua`, `dialogs.lua`, `prompts.lua`) (no vRP NUI). The server keeps every menu, prompt and request per source; the client only shows them and answers on the rate-gated "vRP" tunnel (`validMenuChoice`, `closeMenu`, `promptResult`, `requestResult`, `openMainMenu`), each answer checked against the source it was opened for.

- Server files: `stack.lua` (the menu stack per player; `BridgeVRP.gui` holds what the GUI files share, not an API), `menus.lua` (v1 menus, builders, main menu), `prompts.lua`, `menu_class.lua` (v2 `Menu`), `v2_menus.lua`, `proxy.lua` (v1 proxy functions, the server tunnel), `cleanup.lua`. Client files: `menus.lua` (menus, main menu key), `dialogs.lua` (prompt, request, notifications, text boxes).
- v1 proxy functions (registered by `server/gui/proxy.lua`): `prompt`, `request`, `openMenu`, `closeMenu`, `registerMenuBuilder`, `buildMenu`, `openMainMenu`. Client tunnel / client proxy (`client/gui/`): `notify`, `notifyPicture`, `announce`, `setDiv` / `setDivContent` / `removeDiv` (shown as an ai-lib text box, HTML stripped), `openMenuData`, `closeMenu`, `prompt`, `request`, `getMenuState`.
- `BridgeVRP.ui.prompt(source, title, default[, cb])` -> text (`''` on cancel or drop); waits unless `cb(text)` is given. One prompt per player: a new one answers the old with `''`.
- `BridgeVRP.ui.request(source, text, seconds[, cb])` -> boolean (`false` on no, timeout or drop); waits unless `cb(ok)` is given.
- v1 menus: `BridgeVRP.ui.openMenu(source, menudef[, owner])` (vRP's `menudef`: `name`, `onclose(player)`, choices `[label] = { fn(player, choice, mod), desc }`, sorted by label; replaces the player's open v1 menu, whose `onclose` runs), `BridgeVRP.ui.closeMenu(source)` (closes the top menu, v1 or v2). `BridgeVRP.ui.registerMenuBuilder(name, builder[, owner])` (`builder(add, data)`), `BridgeVRP.ui.buildMenu(name, data)` -> choices (waits for every builder's `add`, at most 5 s). `owner` defaults to `GetInvokingResource()`; a stopped owner's menus and builders go.
- v2 menus (`BridgeVRP.ui.v2`, for the GUI extension): `Menu` (class: `user`, `name`, `data`, `title`, `options`, `css`, `closed`; `listen(event, fn)` for `close` / `remove` / `select`, `triggerEvent`, `addOption(title, action, description, value, index)`, `updateOption(id, title, description)`), `openMenu(user, name, data)` -> menu (`user.source` required; builds with the registered builders, pushes on the player's stack, fires `close` on the previous one), `closeMenu(user[, menu])`, `actualizeMenu(user)`, `closeMenus(user)`, `getMenu(user)`, `registerMenuBuilder(name, builder[, owner])` (`builder(menu)`), `buildMenu(menu)`, `builders` (vRP 2's `GUI.menu_builders`: name -> builder list). v2 `user:prompt` / `user:request` are `BridgeVRP.ui.prompt(user.source, ...)` / `request`.
- v1 and v2 menus share one stack per player; the client shows its top (40 rows a page, paged above that), Escape goes back one menu, holding it closes all. `mod` is always 0 (ai-lib's menu has no left / right). The main menu key (keybind `vrp_main_menu`, default F7; F9 is ai-admin's) appears once a script registers a `main` builder; do not register a default `main` builder.
- Flow: the server sends `openMenuData(menudata)` (fresh `id` per send, also when a vRP 2 menu is built again) or `closeMenu(true)` (hide, nothing sent back) only when the top changed (`shown[source]`). A pick hides the client's dialog, waits for `validMenuChoice` to return (the choice ran, prompts inside it included) and shows the menu again only when no newer `openMenuData` / `closeMenu` arrived meanwhile (net events arrive in order), so a rate-gated or failed pick never strands the menu. `onclose` of a menu replaced by `openMenu` runs in a thread after the new one shows (vRP 1 order); a player close runs it at once and then shows what is on top.
- Panel tab: `VRP_TAB` in `resource/server/vrp/tab.ts` (cards that map rules and groups in `mappingCards.ts`; data spec `schema.ts`; lang keys `ADMIN_*_VRP_*`), rows carry `who` (`readRule` / `readAlias` in `config.ts` keep only that target); `panel.rule("vrp")` refuses a new or changed row whose grade its job / gang lacks. The generic panel pieces it needs (`list` `min` / `search` / `wrap` and row `select` / `grade` / `showIf`, the `grade` and `browse` widgets, lookup `grades`) are in `.claude/rules/admin-panel.md`.

## vRP 2 / 3 (`bridge/vrp/v2/`: `shared/` both sides, `server/`, `client/context.lua`)

- Shared: `owners.lua` (`BridgeVRP2`, owners, `run`), `interfaces.lua`, `context.lua` (the vRP context, extensions, events), `scripts.lua` (`loadScript`). Server: `context.lua` (the server vRP object: users, data, DB), `user.lua` (User object), `base.lua` (`BridgeVRP2.coreExtension`, `vRP.EXT.Base`), one file per core extension (`money`, `group`, `inventory`, `identity`, `survival`, `gui`, `map` = Map, Mission, PlayerState), `lifecycle.lua` (users, events, saves, `loadScript` proxy; after every extension file).

- `BridgeVRP2.loadScript(resource, path, invoker)` (server proxy `loadScript`, client `tvRP.loadScript`) runs the file once in its own environment: a table over `_G` holding `vRP`, an owner-tagging `class`, a per-file `module` (other resources' files load into the same environment; `vrp` files are ai-core's shared ones), and owned versions of `async`, `Citizen.CreateThread(Now)` / `SetTimeout` / `Wait`, `CreateThread`, `SetTimeout`, `Wait`, `AddEventHandler`, `RegisterNetEvent`, `RegisterServerEvent`, `RegisterCommand`, client `RegisterNUICallback`, `Proxy` / `Tunnel` (`addInterface` / `bindInterface` / `getInterface`). Each loaded file is a `VrpOwner`; `onResourceStop` of its resource or of the invoker unloads it (handlers removed, extensions removed with `extension-Unload`, `cleanup` run, `Wait` of its threads raises a sentinel that ends them quietly, commands turn into no-ops).
- Code that registers something on behalf of a script calls `BridgeVRP2.track(undo)` (the undo runs at unload) and reads `BridgeVRP2.owner()` (the script the running thread belongs to; nil = ai-core). Callbacks a script handed over run through `BridgeVRP2.run(owner, fn, ...)` (xpcall, error printed with the file, nothing after unload). `owner.resource` is the resource name to give `BridgeVRP.ui` owners.
- Interfaces are bound once per name (`BridgeVRP2.bind`) with a table that looks the current owner's functions up per call, and `getInterface` tables are cached per name (`BridgeVRP2.interface`): the lib has no unbind, so a restart reuses the handlers instead of adding new ones.
- `vRP.EXT.<core>` are plain tables added with `BridgeVRP2.addExtension` (no class). Server core extensions keep no game logic: every User method calls the vRP 1 function on `BridgeVRP.proxy` with `user.cid` (looked up per call, warns once when missing), menus go to `BridgeVRP.ui.v2` / `prompt` / `request`, and their `remote` is `BridgeVRP.client` (vRP 2's client module functions carry vRP 1's names; vRP 3 additions and `setUserId` / `setCharacterId` are on `tvRP` in `v2/client/context.lua`). A new vRP 2 User method = a function on the module's `*User` table in its `v2/server/<module>.lua`.
- `User` objects use one shared method table rebuilt when an extension comes or goes (core mixins, then extensions' `User` methods in registration order, then User's own), so late extensions reach users already online; a new extension's `User.__construct` runs for them.
- `user.cdata` / `user.data` (extensions' keys) are msgpack in `BridgeVRP.data` key `vRP:datatable` (kinds `c` / `u`), written only when the packed bytes changed (60 s `save`, unload, drop, ai-core stop). The core keys (`wallet`, `bank`, `groups`, `inventory`, `vitals`) are views through `__index` / `__newindex`, never stored.
- Lifecycle: `Bridge.on('loaded')` (in a thread) makes the user (`GetUserId`) and fires `characterLoad` (sync) then `playerJoin`; `Bridge.on('unloaded')` fires `characterUnload`; the bridge's own `playerDropped` fires `characterUnload` when still loaded, then `playerLeave(user, reason)`; `ai-core:playerSpawned` -> `playerSpawn` after 2 s; `ai-core:playerDied` -> `playerDeath`; money / meta / `vRP:playerJoinGroup` deltas -> `playerMoneyUpdate`, `playerVitalChange`, `playerJoinGroup` / `playerLeaveGroup`.

## Wire format (kept from vRP)

- Proxy: `TriggerEvent('<iface>:proxy', member, args, identifier, rid)`, answer `TriggerEvent('<iface>:<identifier>:proxy_res', rid, rets)`; rid -1 = no answer. Tunnel: net event `<iface>:tunnel_req (member, args, identifier, rid)`, answer `<iface>:<identifier>:tunnel_res (rid, rets)`. `args` / `rets` are `table.pack` lists; plain lists (vRP 1.0) are read with `table.maxn`.
- 0.5 style lives in `lib/Proxy.lua` / `lib/Tunnel.lua` (script side): `member({ args }[, cb])` with a pure array; a trailing function in the args is a result callback only for the members in `Proxy.callbackMembers` (`prompt` / `request` callbacks get the player first); a resource's first `getUserId` call fixes its style (`Proxy.style`); ai-core's own runtime is always `'1.0'`. A tunnel call with a function after the args table is 0.5 whatever the style.
- Hardening over vRP: a bound function that errors still answers (empty), a server-side tunnel answer counts only from the asked player, a dropped player's pending requests are answered empty, "not found" prints once per member.

## Data and DB

- `BridgeVRP.data.get(kind, owner, key)` / `set` on `ai_core_vrp_data`: `c` = character (v1 UData, v2 CData), `u` = account (v2 UData), `s` = server (SData; v2 passes the server id as owner), `g` = global. Values cross Lua -> JS as hex (`tohex`), JS keeps them in memory (loaded characters, accounts, every `s` / `g` key) and writes dirty keys within 1 s as 500-row upserts, on unload, stop and txAdmin shutdown. Missing keys answer `''`.
- `BridgeVRP.query(sql, params, mode)` runs vRP's `query` (rows, affected), `execute` (affected), `scalar` (value) with `@name` params; several statements split outside quotes run on one connection in a transaction. The prepared names (`vRP.prepare`) are kept in Lua per calling resource (W2).
- Permission mapping: export `GetVrpConfig()` (type `VrpConfig` in `@aicore-fivem/shared` `vrp.ts`) and local event `ai-core:vrp:config (config)` after a panel change; `VrpPermissionAsked(perm)` records a string scripts asked for (call it once per string per runtime). Matching (W2): a rule whose `permission` names the asked string (exact, or prefix before a trailing `*`) grants it to whoever matches any filled target (`everyone`, `admin`, `job` + `grade` + `onDuty`, `gang` + `grade`, `group` = extra group); when any rule names the string, the built-in `defaults` are not consulted; otherwise `<job>.*` (on duty with `jobOnDuty`), `admin.*`, `player.*`. vRP 1.0's special forms keep their meaning: `!name.args` permission functions (`not`, `is`, `registerPermissionFunction`), `#item.op` item counts, `@...` aptitudes (false); only plain strings are recorded as asked.
