# ai-core

The framework resource: accounts (FiveM id), characters and the character screen, money accounts with a ledger, multi-job and multi-gang with duty, paycheck, ACL mirror, persistence, exports and events. Uses the database through `@aicore-fivem/mysql` (own pool; needs its `add_convar_permission` line). Jobs and gangs design: `resource/server/jobs/CLAUDE.md`; data model reasoning: the `aicore-fivem` skill (`references/data.md`).

## Decisions

- The account key is the FiveM id (`fivem:` identifier, owner decision); connecting without one is refused in `playerConnecting`. license and discord are stored next to it for bridges.
- The character screen is part of ai-core (owner decision: UI now, not a separate script) and follows `docs/design.md` (TGIANN style, tgiann-multichar sibling): the UI floats with a light vignette over an in-world scene (`characterScene` in settings, default tgiann-multichar's "city" set): each character stands as a local ped in its saved look on the spot of its slot, playing the spot's idle, and the camera glides to the picked one; the player waits hidden under the scene; `branding.background` shows only when the scene cannot be built. "Choose character" title and the picked character's details on the left, server brand and tagline (`branding` in settings) bottom left, a bottom row of round character slots and green-plus free slots, delete + PLAY pill bar bottom right; creating is its own full-screen view (pill form on the right), deleting a TGIANN confirm popup. Card portraits come from an appearance resource (ai-appearance): ai-core emits `characterScreen (src, charIds)` each time the screen loads and shows what arrives on `ai-core:client:characterPortrait (charId, url)` (only `https://nui-img/` urls); a slot without one shows the initials. Scene peds get their look through ai-core's own appearance layer: on `characterScreen` the server reads each card's look from the active clothing script and sends them latent as `ai-core:client:characterLooks`; the scene creates a ped with the look's model and dresses it (default freemode clothes without a clothing script); the scene forces its own time and weather with the weather sync paused (`qb-weathersync:client:DisableSync` / `EnableSync`) and clears everything on spawn, resource stop or a failed build. Mechanism: `resource/client/CLAUDE.md`. Behind the NUI the player waits in a private routing bucket from the bucket allocator (population off, strict lockdown, given back on spawn or drop); no spawnmanager.
- Default accounts `cash`, `bank`, `black_money`, `crypto` (owner decision), defined in `data/accounts.json`. Character accounts start with the type's starting amount; job and gang accounts start empty and load once at start, so the society money exports stay synchronous.
- Money is memory-first: a change is checked and applied synchronously, then goes to the money writer (`money/writer.ts`), which sends every account's changes of 50 ms as one transaction (summed `balance = balance + v.d` per account, multi-row ledger insert), in order. Only ai-core writes balances. Stress numbers: the `aicore-fivem` skill's `references/scale.md`, benches in `bench/` (separate `ai_core_stress` database).
- Jobs: several per character up to `maxJobs` (one when `multiJob` is off, a new job replaces the old), at most one on duty, salary only from the on-duty job. Duty is runtime state, off after joining unless `restoreDuty`; the last duty job is kept in metadata (`lastDutyJob`). The unemployed job is never stored. Gangs follow the same rules with one active gang (saved).
- Prime time (owner decision): the paycheck can lower salaries outside a job's prime time (`settings.primeTime`, grade `offPrimePayment`); hours come from a script that keeps them (tgiann-policealert, `jobs/primeTime/registry.ts`) while it runs, else ai-core's panel hours (`resource/server/jobs/CLAUDE.md`, `docs/compat/prime-time.md`).
- Memberships are mirrored to ACL principals `ai.job.<name>` and `ai.job.<name>.<grade>` (every grade up to the player's), same for gangs, on `player.<source>`.
- Position and metadata are written by the periodic flush (`saveIntervalMinutes`), on unload, on resource stop and on txAdmin shutdown; money and memberships are written as they change.
- Panel content (`data/settings.json`, `accounts.json`, `jobs.json`, `gangs.json`) is kept by ai-core's own `AdminPanel` (`resource/server/content`) and edited live in the panel; ai-core also hosts the panel for every other script (`resource/server/admin/CLAUDE.md`).
- Dev test commands `aicore_switch`, `aicore_job`, `aicore_duty`, `aicore_money`, `aicore_gang`, `aicore_db [slow]` (database statistics of every resource), `aicore_alert [high]` (a test police alert through the active alert system) are lib `addCommand`s restricted to admins, answer in the server console and exist only until the admin panel covers them.
- ai-core keeps the server's command list and every keybind's default key for the panel (`resource/server/admin/CLAUDE.md`): lib `addCommand` announces commands through the `RegisterCommands` export; lib `Keybind`s announce themselves to ai-core's client, which answers each with its default key (panel `data/keybinds.json`, `sync: "all"`, else the script's key).
- Items go through ai-core (owner decision: one change reaches every script): the inventory layer (`resource/server/inventory/`, `docs/compat/inventory.md`) forwards to the active inventory through one adapter file per inventory, picked by the panel setting `inventory` (`auto` = first running in registry order) and again on inventory start / stop; it keeps usable items and stashes and hands them to every inventory that becomes active. The bridge's item functions use the same layer; ai-inventory must never call it (loop).
- Vehicle keys go through ai-core the same way (owner decision): the key layer (`resource/server/vehicleKeys/`, `docs/compat/vehicle-keys.md`) forwards to the active key system through one adapter file per system (client-API-only systems through `resource/client/vehicleKeys/adapters/`), picked by the panel setting `vehicleKeys`; with none running every key counts as held.
- Every integration layer picks its adapter with `AdapterPicker` (`resource/common/adapters.ts`; client halves of server picks follow the published GlobalKey with `AdapterFollower`): the panel's choice or the first running adapter in registry order, picked again when a candidate starts or stops. A stopping resource and the names it `provide`s count as stopped until it starts again (they still read started during the stop: ai-vehiclekeys `provide`s qbx_vehiclekeys). `call(what, fn, fallback)` is the one try / catch that logs and falls back. A new category = a registry list plus a picker.
- Looks go through ai-core's appearance layer (owner decision: any script reads and applies looks, other clothing scripts get supported): `resource/server/appearance/` reads a character's stored look `{ model, data }` from the active clothing script (panel setting `appearance`; tgiann-clothing, ai-appearance last), `resource/client/appearance/` applies it to a ped of that model through the same script's client adapter (pick published in GlobalState `ai:appearance`); lib `appearance`, `docs/compat/appearance.md`. tgiann-clothing replaces ai-appearance (`STAND_INS`).
- Deaths and revives go through ai-core's medical layer (`resource/server/medical/`, lib `medical`): the first running death script (ai-death) answers revive, heal and the down state; admin tools never call a death script.
- Routing buckets come from one allocator (`resource/server/buckets/`, lib `buckets.acquire(tag)` / `release(id)`): ids from 1000 up, released ones reused, each held by the resource that took it and freed when it stops; never `base + n` per script.
- Police alerts go through ai-core the same way (owner decision): the dispatch layer (`resource/server/dispatch/`, `docs/compat/dispatch.md`) forwards lib `dispatch.alert` to the active alert system (panel setting `dispatch`; ai-policealert's built-in cards come last in the order) and answers QB's `police:server:policeAlert` for systems that do not.
- Update check (`resource/server/versions.ts`): every started script with a GitHub `repository` line in its fxmanifest (ai-* scripts write it from package.json `repository`) is compared with its latest GitHub release, at most once per 6 h per script (answer kept in server KVP `update:<resource>`, so restarts do not ask again) and when a script starts; outdated ones are warned once in the console and listed on the admin dashboard. Panel: General, Updates (`updates.check`, `updates.ignore`). Unauthenticated GitHub allows 60 requests an hour per server IP.
- Script recommendations (owner decision: free scripts worth installing; `resource/server/recommendations/`): each entry in `RECOMMENDATIONS` (`index.ts`) has an id (the product's resource name), title and one-line why (ai-core lang keys `ADMIN_REC_<NAME>` / `_DESC`), the product url, `free` (the dashboard shows a "Free" chip) and `shows(runs)`, its condition (`runs(resource)` = started and not stopping; tgiann-phone: no phone in ai-core's phone layer, `phones.active === null`; tgiann-esc-map: that resource does not run). Adding one = one entry plus its two lang keys; a condition on another ai-core layer uses that layer's picker (`onSwitch` re-checks). Conditions are re-checked on resource start / stop, phone layer switches and settings changes (no polling); the shown ones go into the admin open answer (`AdminOpenData.recommendations`) and to admins with the panel open as `RecommendationDelta` (`ai-core:admin:recommendation`, NUI `adminRecommendation`), and are printed once in the console 15 s after start (`ADMIN_REC_CONSOLE`). The owner dismisses one with the card's X (settings `recommendations.dismissed`, ids; the card hides at once from the panel's own settings copy) and brings it back by removing the id in General, Recommendations. Web: `features/admin/Recommendations.tsx` (dashboard section under Updates) and `recommendationActions.ts` (open snapshot, deltas, dismiss; "Open page" calls FiveM's `invokeNative("openUrl", url)` in game, a new tab in the browser preview). The schema section and card live in `recommendations/schema.ts` because the web preview imports the panel schema (no FiveM code there).
- Setup guide (owner decision): while ai-core's `setupDone` setting is off, every player who spawns gets a welcome card (`resource/server/setup.ts`, `client/setup.ts`): admins open the panel from it, which starts on the setup guide (web `Setup.tsx`); others see the `add_principal identifier.fivem:<id> group.admin` line to copy into permission.cfg. The guide's last step turns `setupDone` on.
- Connecting goes through one gate (`resource/server/connection/`): ai-core's checks (a FiveM account; no unneeded script running next to its replacement, panel switch `refuseOnConflict`) and the checks other resources add with `AddConnectionCheck`. Unneeded scripts (owner decision: a server owner who installs tgiann-inventory is told to delete ai-inventory) come from built-in rules (ai-* stand-ins, every inventory and key adapter), `ai_replaces '<resource>'` lines in any fxmanifest and `RegisterReplacement`; the console names the folder to delete, and while both run nobody can join.
- The ESX/QB/Qbox bridge is part of ai-core (owner decision): it `provide`s `es_extended`, `qb-core` and `qbx_core` and answers their exports, core objects and events from Lua files in `bridge/`, so other scripts use ai-core as their framework (`.claude/rules/lua-bridges.md`, `docs/compat/README.md`).
- Every ai-* resource logs through ai-core (`Log` export, lib `aiLog`), like tgiann-core: resources name channels, ai-core sends to the providers its panel turns on (`data/logs.json`: console, Discord, Fivemanage, FiveM Stats; minimum level, ip on/off). Webhook urls and the Fivemanage key are panel-edited too, but in `data/secrets.json` (git-ignored: `discordWebhooks` by `<resource>/<channel>`, `<resource>` or `default`, `fivemanageKey`); env.cfg is not used for them (owner decision). ai-core logs its own events (characters, money, jobs, gangs, client errors) from its local events in `logs/coreEvents.ts`.

## Contracts

- Exports: typed in `@aicore-fivem/shared` `exports.ts` (`AiCoreServerExports`, `AiCoreClientExports`), registered in `resource/server/exports.ts` and `client/playerState.ts`.
- Server local events (`CORE.*` in `@aicore-fivem/shared`): `playerLoaded (src, CharacterInfo)`, `playerUnloaded (src, charId, "dropped" | "switch")`, `moneyChanged (src, account, balance, delta, reason)`, `jobsChanged`, `dutyChanged`, `gangsChanged`, `activeGangChanged`. Client: `client:playerLoaded (AiPlayerData)`, `client:playerUnloaded`.
- Player data channel to the owner's client: snapshot at load, then `(key, value)` deltas; `money` travels as patches of the changed accounts only (`PLAYER_DATA_PATCH_EVENT`). Client side: lib `onPlayerData` / `getPlayerData`, `GetPlayerData` export for late starters.
- GlobalState `ai:duty:<job>`: on-duty count per job; `ai:inventory` / `ai:vehicleKeys` / `ai:appearance`: the active inventory's, key system's and clothing script's resource names (client adapter pick).
- Connection and conflict exports: `AddConnectionCheck(id, (source, identifiers) => reason | null)`, `RegisterReplacement(remove, keep?)` (keep defaults to the caller), `GetConflicts()`.
- Vehicle key exports `GiveVehicleKeys`, `RemoveVehicleKeys`, `HasVehicleKeys` (source, entity or plate), typed `VehicleKeysServerExports`; server -> client `ai-core:client:vehicleKeys (action, netId, plate)` for client-API-only systems.
- Inventory exports (server `AddItem`, `RemoveItem`, `GetItemCount`, `HasItem`, `CanCarryItem`, `GetItems`, `ClearInventory`, `RegisterStash`, `OpenInventory`, `RegisterUsableItem`, `GetItemDefinition(s)`, bridge-only `UseItem` / `IsUsableItem`; client `OpenInventory`, `HasItem`, `GetCurrentWeapon` (the held weapon item, `HeldWeapon`)), typed `InventoryServerExports` / `InventoryClientExports`; local events `inventoryChanged (resource | null)`, `itemUsed (src, name, status | null)`.
- Client exports `ShowPrompt(id, text)` / `HidePrompt(id)` (lib `showPrompt` / `hidePrompt`): the right-side prompt UI, one interaction keybind (`aicore_interact`, mapping `+aicore_interact_<key>`) tells the resource of the prompt on top through `ai-core:client:promptPressed (resource, id)`; a stopped resource's prompts go with it.
- Client exports `Notify(notification)`, `ShowProgress(label, ms)`, `HideProgress()` and server -> client `ai-core:client:notify`: notification cards (top right) and the progress bar (bottom centre) for every resource through lib `notify` / `progress`; the calling resource runs the timer and animation, ai-core only draws.
- Export `GetUpdates()`: the outdated scripts (`UpdateInfo`).
- Dispatch export `SendDispatchAlert(alert) -> boolean` (`DispatchAlert` in `@aicore-fivem/shared` `dispatch.ts`, lib `dispatch`); ai-core answers `police:server:policeAlert` (client `(text)`, server `(text, camId, playerSource)`).
- Export `IsPrimeTime(job?) -> boolean` (lib `isPrimeTime`): prime time of a job (default hours without one) from the active prime time source; works whether or not the salary cut is on.
- Money transfer export `TransferMoney(from, to, amount, reason?, fee?)` (lib `money.transfer`; `MoneyRef` = `{ source, account }` or `{ owner: "job" | "gang", id, account }`): both changes apply synchronously, so they share one money writer batch (one transaction, both ledger rows); `from` also pays `fee`.
- Bucket exports `AcquireBucket(tag) -> id` / `ReleaseBucket(id) -> boolean` (lib `buckets`); medical exports `RevivePlayer`, `HealPlayer`, `IsPlayerDead`, `GetMedicalSystem` (lib `medical`); `SetOfflinePosition(charId, { x, y, z, heading? })` (lib `characters.setOfflinePosition`): a stored character's spawn point, written once no load or unload save holds it, false while the character is loaded.
- Phone exports `GetPhoneNumber`, `GetSourceByPhone`, `HasPhone`, `SendPhoneMail`, `SendPhoneMessage`, `PhoneNotify` (`resource/server/phone/`, first running phone: tgiann-phone, lb-phone), lib `phone`, `docs/compat/phone.md`.
- Time and weather exports `GetWeather`, `SetWeather`, `GetTime`, `SetTime`, `SetBlackout`, `FreezeTime` (server, `resource/server/world.ts`, the qb-weathersync contract) and `PauseWorldSync` / `ResumeWorldSync` (client, counted reasons); lib `world` on both sides, `docs/compat/weather.md`.
- Appearance exports: server `GetAppearanceSystem()`, `GetCharacterAppearance(charId, done)` (a callback: the look or null); client `ApplyAppearance(ped, look)`, `GetPedAppearance(ped)` (lib `appearance`, `docs/compat/appearance.md`).
- Client exports `GetGestureProvider()`, `IsHandsUp()`, `IsPointing()` (lib `gestures`, `resource/client/gestures.ts`): the first running emote script answers (tgiann-emotes, ai-smallresources), `docs/compat/gestures.md`.
- Client exports `AddRadialItem(RadialItem)`, `RemoveRadialItem(id)`, `RefreshRadial()` (lib `radial`, `resource/client/radial/`): the radial layer keeps every resource's wheel items (dropped when that resource stops) and hands them to the first running radial through its adapter (ai-radialmenu, tgiann-radialmenu-target, qb-radialmenu, ox_lib), again to a radial that starts or restarts; `docs/compat/radial.md`.
- Client exports `HideHud(reason)` / `ShowHud(reason)` / `IsHudVisible()` (lib `hud`, `resource/client/hud.ts`): HUDs hide while any full-screen UI holds a reason (`<resource>:<reason>`, dropped when that resource stops); local event `CORE.clientHudVisibleEvent (visible)` for HUDs that listen (ai-hud), adapters for others (tgiann-lumihud's `tgiann-lumihud:ui`); without such an adapter ai-core toggles the minimap.
- Client local event `ai-core:client:cache (key, value)`: ai-core's one 100 ms watcher of ped, vehicle, seat and weapon feeds every resource's lib `cache`.
- Keybinds (`KEYBIND` in `@aicore-fivem/shared`): client local `ai-core:client:keybind (KeybindInfo)` from the lib, answered with `ai-core:client:keybindKey (resource, name, key)`; client export `GetKeybindKey(name)` gives the key a keybind was registered with.
- Key hints (`KEY_HINTS` in `@aicore-fivem/shared`, `resource/client/keyHints.ts`): the list of keys a HUD shows on the left, built from keybinds declared with `hint` (shown on foot, in a vehicle or always; the panel's per-keybind choice wins over the script's) plus dynamic hints of client exports `ShowKeyHint(id, key, label)` / `HideKeyHint(id)` (lib `keyHints`; a stopped resource's hints go with it). Each hint may carry a Font Awesome `icon` (Keybind `icon` option, `ShowKeyHint`'s `icon`) and shows the keybind's short `hintLabel` instead of its description. Recomputed on keybind changes and vehicle enter / exit; local event `ai-core:client:keyHints (KeyHintView[])`, export `GetKeyHints()` for a HUD that starts later. The bound key is read with `GetControlInstructionalButton` on `+<name>_<key>` (`t_` prefix stripped), so a player's own rebinding shows.
- Item picker (`resource/client/itemPicker.ts`, web `features/dialogs/ItemPicker.tsx` + `PickedList.tsx`, lib `itemPicker`): client export `OpenItemPicker(id, { title, target? })` asks the server for the active inventory's items and the target's weight (`ITEM_PICKER_CALLBACK`, admins only; pictures from the adapter's `image` url, weight from the adapter's optional `getWeight`) and shows a searchable picture grid; clicks fill a list on the right (1, Ctrl 10, Shift 100; each row has -10 / count / +10) that stops at the weight limit; Take answers the list once (`menuResult`). Admin tools only: the caller's server gives and checks every item.
- Keys screen (`resource/client/keyboard.ts`, web `features/keyboard/`): client export `OpenKeyboard()` (the radial menu's Keys entry) shows a keyboard with every key a lib keybind has (the player's own binding) coloured, a search over actions and scripts (matching keys stay coloured), and the actions of the key under the pointer (kept while the pointer crosses gaps, reset when it leaves the keyboard).
- Dialogs (menu, input, item picker, keys screen) close on Escape when it comes up, and the client blocks the pause controls (199, 200) for 500 ms after any of them closes: closing on the press hands the release to the game, which opens the pause menu. Menu rows with `checked` are switch rows flipped in place (`MENU_EVENTS.menuToggle`); the row under the pointer takes the focus, so one row is highlighted at a time.
- HUD settings: client exports `OpenHudSettings()` / `HasHudSettings()` open whichever HUD's own settings menu runs (ai-hud's `OpenSettings` export, tgiann-lumihud's `/hud`); the radial menu's HUD entry uses them. Server export `RegisterCommands(resource, CommandInfo[])` (lib `addCommand`).
- Character screen looks and portraits: server local `characterScreen (src, charIds)` (ai-core answers with the latent `ai-core:client:characterLooks ({ id, look }[])`), client local `client:characterPortrait (charId, url)`; the client keeps them until a character spawns and sends them with the open payload and as `portrait` messages.
- Callbacks: `ai-core:characters`, `createCharacter`, `selectCharacter`, `deleteCharacter`; server → client `ai-core:client:spawn (SpawnPoint)`, `ai-core:client:openCharacters`.
- NUI contract: `resource/common/nui.ts`; the open message carries `{ screen, texts, portraits, scene }` (lang table from `loadLocaleTexts`; `scene` false = show the background picture); picking a card calls `focus (characterId)`.
- `ai-core:clientError` (client → server): client script errors, logged on channel `clientErrors` (level error) as `[client error] <resource>: ...` with the player.
- Exports `Log(channel, message, { level, source, target, metadata })` and `LogChannels({ [channel]: { dataset, active } })`; types in `@aicore-fivem/shared` `logs.ts`.
- Bridge (`bridge/`, `docs/compat/bridge.md`): the server part mirrors loaded players from ai-core's local events (`bridge/core/server.lua`) and sends the client part one snapshot (`ai-core:bridge:snapshot`) then patches (`ai-core:bridge:patch`: money, job, gang); the client fires QB / ESX client events locally. Provides `es_extended`, `qb-core`, `qbx_core`.
- Tables: `ai_core_users`, `ai_core_characters` (soft delete `deleted_at`), `ai_core_accounts` (`owner_type` character/job/gang, `owner_id` as text), `ai_core_transactions`, `ai_core_character_jobs`, `ai_core_character_gangs`.

## Pitfalls

- `ai_core_accounts.owner_id` is text: compare with `CAST(id AS CHAR) COLLATE utf8mb4_unicode_ci` in joins. Without the cast the unique key is not used; without the COLLATE the cast takes the connection's `utf8mb4_general_ci` and MariaDB refuses the comparison ("Illegal mix of collations").
- `mysql.transaction` answers `false` on rollback without throwing; `Account.change` turns that into an error so the write queue logs it.
- The dev commands answer in the server console (`print`), not in ai-chat (only `addCommand`'s own errors are notifications); the system chat is off (`resources_useSystemChat false`) because ai-chat provides `chat`.

## Entry points

- Framework bridge: shared mirror `bridge/core/server.lua` and `client.lua`, one folder per framework (`bridge/qb`, `bridge/qbx`, `bridge/esx`).

- Connection, character screen callbacks, load/unload/switch: `resource/server/player/session.ts`; card data `player/screen.ts`.
- Loaded player: `player/player.ts` (with `wallet.ts`, `../jobs/jobSet.ts`, `../jobs/gangSet.ts`).
- Money: `money/account.ts` (one account), `money/book.ts` (loading, job/gang accounts).
- Panel content and defaults: `content/index.ts`.
- Saving: `persistence.ts`; paycheck `jobs/paycheck.ts`, prime time `jobs/primeTime/`.
- Logs: dispatch `logs/index.ts`, providers `logs/discord.ts` (rate-limited queue per webhook) and `logs/services.ts` (Fivemanage batches, FiveM Stats, console), settings and webhook lookup `logs/settings.ts`.
- Client: boot `resource/client/index.ts`, screen and spawn `client/characters.ts`, scene and its peds `client/scene.ts`, camera `client/sceneCamera.ts`; scene panel data `server/content/scene.ts`, its panel tab `server/admin/sceneSchema.ts`.
- NUI: `web/src/features/characters/` (store, actions, panel); browser preview `bun run webdev` with `?view=create|delete|error` (`&scene` = transparent, as over the game scene).
