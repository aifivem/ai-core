# ai-core

The framework resource: accounts (FiveM id), characters and the character screen, money accounts with a ledger, multi-job and multi-gang with duty, paycheck, ACL mirror, persistence, exports and events. Uses the database through `@aicore-fivem/mysql` (own pool; needs its `add_convar_permission` line). Jobs and gangs design: `resource/server/jobs/CLAUDE.md`; data model reasoning: the `aicore-fivem` skill (`references/data.md`).

## Decisions

- The account key is the FiveM id (`fivem:` identifier, owner decision); connecting without one is refused in `playerConnecting`. license and discord are stored next to it for bridges.
- The character screen is part of ai-core (owner decision: UI now, not a separate script) and follows `docs/design.md` (TGIANN style, tgiann-multichar sibling): the UI floats with a light vignette over an in-world scene (`characterScene` in settings, default tgiann-multichar's "city" set): each character stands as a local ped in its saved look on the spot of its slot, playing the spot's idle, and the camera glides to the picked one; the player waits hidden under the scene; `branding.background` shows only when the scene cannot be built. "Choose character" title and the picked character's details on the left, server brand and tagline (`branding` in settings) bottom left, a bottom row of round character slots and green-plus free slots, delete + PLAY pill bar bottom right; creating is its own full-screen view (pill form on the right), deleting a TGIANN confirm popup. Card portraits come from an appearance resource (ai-appearance): ai-core emits `characterScreen (src, charIds)` each time the screen loads and shows what arrives on `ai-core:client:characterPortrait (charId, url)` (only `https://nui-img/` urls); a slot without one shows the initials. Scene peds get their look through ai-core's own appearance layer: on `characterScreen` the server reads each card's look from the active clothing script and sends them latent as `ai-core:client:characterLooks`; the scene creates a ped with the look's model and dresses it (default freemode clothes without a clothing script); the scene forces its own time and weather with the weather sync paused (`qb-weathersync:client:DisableSync` / `EnableSync`) and clears everything on spawn, resource stop or a failed build. Mechanism: `resource/client/CLAUDE.md`. Behind the NUI the player waits in a private routing bucket from the bucket allocator (population off, strict lockdown, given back on spawn or drop); no spawnmanager.
- Choosing where to appear (qb-spawn / qbx_spawn's job, owner decision: part of ai-core like the character screen): with the panel's `spawn.choose` on and at least one place in `spawn.points`, picking a character loads it (`playerLoaded` fires) but the spawn waits: the server sends the options (`CORE.chooseSpawnEvent`: the last location for a stored character, then the places), ai-core's menu lists them over the character scene (`client/spawnChoice.ts`, closing keeps the first), and `CORE.spawnChoiceCallback (id)` picks one of the server's own points before `spawnEvent` goes out.
- External character screens (owner decision: ai-core's screen is built in and cannot be removed, so it steps aside): `resource/server/multichar/` picks the screen with `AdapterPicker` (panel `characterScreen`: `auto` = the first running multichar of `MULTICHARS`, else ai-core; a picked one that does not run leaves ai-core's on), publishes it in GlobalState `ai:characterScreen` and prints `characterScreenChanged: ...`. While one runs ai-core opens no screen, uses no select bucket, upserts the account at `playerJoining` and logs players in only through the login exports; the multichar spawns the ped, ai-core sends `externalLoadedEvent` instead of its spawn and fires `playerSpawned` when the client reports the player in the world (`player/spawn.ts`, `client/multichar.ts`). The ESX / QB tables multichars read (`players`, `users`, `jobs`, `job_grades`) are ai-core-made projections for connected accounts only (panel `frameworkTables`; marked by table comment, a real framework table is never touched; a delete through them soft-deletes the character by trigger). Mechanism: `resource/server/multichar/CLAUDE.md`; scripts, tables and bridge calls: `docs/compat/multichar.md`.
- Default accounts `cash`, `bank`, `black_money`, `crypto` (owner decision), defined in `data/accounts.json`. Character accounts start with the type's starting amount; job and gang accounts start empty and load once at start, so the society money exports stay synchronous.
- Money is memory-first: a change is checked and applied synchronously, then goes to the money writer (`money/writer.ts`), which sends every account's changes of 50 ms as one transaction (summed `balance = balance + v.d` per account, multi-row ledger insert), in order. Only ai-core writes balances. Stress numbers: the `aicore-fivem` skill's `references/scale.md`, benches in `bench/` (separate `ai_core_stress` database).
- Jobs: several per character up to `maxJobs` (one when `multiJob` is off, a new job replaces the old), at most one on duty, salary only from the on-duty job. Duty is runtime state, off after joining unless `restoreDuty`; the last duty job is kept in metadata (`lastDutyJob`). The unemployed job is never stored. Gangs follow the same rules with one active gang (saved).
- Prime time (owner decision): the paycheck can lower salaries outside a job's prime time (`settings.primeTime`, grade `offPrimePayment`); hours come from a script that keeps them (tgiann-policealert with its one-line `IsPrimeTime` export patch, `jobs/primeTime/registry.ts`) while it runs, else ai-core's panel hours (`resource/server/jobs/CLAUDE.md`, `docs/compat/prime-time.md`).
- PvP (QB `PVP`): panel setting `pvp` (General, default on) published as GlobalState `ai:pvp` (`server/pvp.ts`); every client applies it to its ped (`SetCanAttackFriendly` + `NetworkSetFriendlyFireOption`, again on a new ped, `client/pvp.ts`); `/togglepvp` (admins) flips the setting.
- Memberships are mirrored to ACL principals `ai.job.<name>` and `ai.job.<name>.<grade>` (every grade up to the player's), same for gangs, on `player.<source>`.
- Position and metadata are written by the periodic flush (`saveIntervalMinutes`), on unload, on resource stop and on txAdmin shutdown; money and memberships are written as they change. Body armour is sampled from the ped (server `GetPedArmour`) at each of those saves into metadata `armor` (QB's key, so the QB mirror shows it), goes to the client in the spawn point and is set on the ped after the spawn, and again on a ped a clothing script swaps in within 15 s (`client/armour.ts`).
- Characters carry a free-text `nationality` (column, 2-32 letters, `toNationality` in `@aicore-fivem/shared`): asked in the create form, edited in the Players section, empty (`''`) for characters made before the column; QB `charinfo.nationality` (ESX has no such field).
- Panel content (`data/settings.json`, `accounts.json`, `jobs.json`, `gangs.json`) is kept by ai-core's own `AdminPanel` (`resource/server/content`) and edited live in the panel; ai-core also hosts the panel for every other script (`resource/server/admin/CLAUDE.md`).
- Dev test commands `aicore_switch`, `aicore_job`, `aicore_duty`, `aicore_money`, `aicore_gang`, `aicore_db [slow]` (database statistics of every resource), `aicore_alert [high]` (a test police alert through the active alert system) are lib `addCommand`s restricted to admins, answer in the server console and exist only until the admin panel covers them.
- ai-core keeps the server's command list and every keybind's default key for the panel (`resource/server/admin/CLAUDE.md`): lib `addCommand` announces commands through the `RegisterCommands` export; lib `Keybind`s announce themselves to ai-core's client, which answers each with its default key (panel `data/keybinds.json`, `sync: "all"`, else the script's key).
- Items go through ai-core (owner decision: one change reaches every script): the inventory layer (`resource/server/inventory/`, `docs/compat/inventory.md`) forwards to the active inventory through one adapter file per inventory, picked by the panel setting `inventory` (`auto` = first running in registry order) and again on inventory start / stop; it keeps usable items and stashes and hands them to every inventory that becomes active. The bridge's item functions use the same layer; ai-inventory must never call it (loop).
- Vehicle keys go through ai-core the same way (owner decision): the key layer (`resource/server/vehicleKeys/`, `docs/compat/vehicle-keys.md`) forwards to the active key system through one adapter file per system (client-API-only systems through `resource/client/vehicleKeys/adapters/`), picked by the panel setting `vehicleKeys`; with none running every key counts as held.
- Every integration layer picks its adapter with `AdapterPicker` (`resource/common/adapters.ts`; client halves of server picks follow the published GlobalKey with `AdapterFollower`, `common/adapterFollower.ts`): the panel's choice or the first running adapter in registry order, picked again when a candidate starts or stops. A stopping resource and the names it `provide`s count as stopped until it starts again (they still read started during the stop: ai-vehiclekeys `provide`s qbx_vehiclekeys). `call(what, fn, fallback)` is the one try / catch that logs and falls back. A new category = a registry list plus a picker.
- Looks go through ai-core's appearance layer (owner decision: any script reads and applies looks, other clothing scripts get supported): `resource/server/appearance/` reads a character's stored look `{ model, data }` from the active clothing script (panel setting `appearance`; the scripts in `docs/compat/appearance.md`, ai-appearance last), `resource/client/appearance/` applies it to a ped of that model through the same script's client adapter (pick published in GlobalState `ai:appearance`); lib `appearance`, `docs/compat/appearance.md`. Every clothing script of the registry makes ai-appearance unneeded (conflict rules built from `APPEARANCE_SYSTEMS`).
- Deaths and revives go through ai-core's medical layer (`resource/server/medical/`, lib `medical`, `docs/compat/medical.md`): the first running death script (ai-death, qbx_medical, ars_ambulancejob, qb-ambulancejob, esx_ambulancejob) answers revive, heal and the down state; admin tools never call a death script. The client half (`resource/client/medical/`) follows the pick (GlobalState `ai:medical`) and keeps the local player's down state for every resource (export `IsDead`, local event `CORE.clientDeadEvent`, lib client `medical.isDead()`).
- Fuel, door locks and garages go through ai-core the same way (`resource/server/fuel/`, `doorlock/`, `garages/`; panel settings `fuel`, `doorlock`, `garages`; ai-fuel, ai-doorlock, ai-garages first in their registries; `docs/compat/fuel.md`, `doorlock.md`, `garages.md`). Fuel is the `fuel` bag for every script: server-side scripts keep it, for client-side ones (LegacyFuel style exports) ai-core mirrors it from driver reports and hands server sets to the entity's owner client through the pending bag `ai:fuelSet` (`resource/client/fuel/`). Doors are named by the active script's own id. Garage scripts answer only the actions they expose (impound, store, open, list); client-API ones get them on the acting player's client (`resource/client/garages/`).
- Routing buckets come from one allocator (`resource/server/buckets/`, lib `buckets.acquire(tag)` / `release(id)`): ids from 1000 up, released ones reused, each held by the resource that took it and freed when it stops; never `base + n` per script.
- Export providers own other resources' entries through the lib: `caller()` names the calling resource, `ByResource` holds entries that go when it stops (bucket leases, log channels, external panels, the item picker's open dialog), `Reasons` holds the HUD-hidden and world-sync-paused reasons (ai-core's own screens pass `CORE.resource` as the owner; third-party weather pause events are owned by `external`). Key hints, radial items and connection checks keep a plain Map keyed by `caller()` with their own stop listener: their order across resources is visible (hint list, wheel order after a radial restart, first refusal wins), and `ByResource` groups entries by owner.
- Notifications stay ai-lib's cards unless the owner picks another UI (panel setting `notify`, default `ai-lib`, no automatic pick so an installed ox_lib never takes over): `resource/server/notify/` publishes the pick in GlobalState `ai:notify`, ai-lib hands each card to ai-core's client (`ExternalNotify`, adapters in `resource/client/notify.ts`), ai-lib draws it itself while the key is unset (also without ai-core).
- Police alerts go through ai-core the same way (owner decision): the dispatch layer (`resource/server/dispatch/`, `docs/compat/dispatch.md`) forwards lib `dispatch.alert` to the active alert system (panel setting `dispatch`; ai-policealert's built-in cards come last in the order) and answers QB's `police:server:policeAlert` for systems that do not.
- Bills, banking, MDT records and medics go through ai-core layers the same way (panel settings `billing`, `banking`, `mdt`, `ems`; cards from `server/admin/schema/services.ts`): billing (`server/billing/`) sends job or player bills to the active billing script, else to ai-core's own bills (`billing/builtin.ts`), which always run: open bills are rows of `ai_core_bills` by character id (offline characters too, lib `toCitizenid`; the insert checks the character and the 20-open cap), a loaded character's are read once at load and kept in memory, paying is one `transferMoney` with the row's delete attached to the same money writer batch (`moneyWriter.attach`: one transaction, so bill and money never drift); banking (`server/banking/`) opens a banking script, reports society balances and links the script's job / gang accounts to ai-core's job / gang `bank` accounts through its documented exports (`banking/link.ts`, adapter `accounts`), by the panel setting `bankAccounts`: `core` (default: ai-core holds the money; each change is written to the script with its set export, one write per account per tick, and changes made in the script come back through its hook as the same delta; a `writing` flag and the last balance the script shows drop ai-core's own echo; ai-core's balance wins on every activation) or `own` (the script holds the money: `Account` reads and changes of a linked account go to the script's exports synchronously through `linkSharedAccounts`, a `false` answer is a failed change, ai-core's rows stay untouched), `docs/compat/banking.md`; MDT (`server/mdt/`, client `client/mdt/` following GlobalState `ai:mdt`) has no ai-* default, so records go nowhere without one; EMS (`server/ems/`) asks the active script for free medics or a distress call and answers what it lacks itself (duty counts, a dispatch alert). Built-in parts that must not import content-dependent code sit outside the registries (`BILLING_CHOICES`, `EMS_CHOICES` give the panel their names). `docs/compat/billing.md`, `banking.md`, `mdt.md`, `ems.md`.
- Update check (`resource/server/versions.ts`): every started script with a GitHub `repository` line in its fxmanifest (ai-* scripts write it from package.json `repository`) is compared with its latest GitHub release, at most once per 6 h per script (answer kept in server KVP `update:<resource>`, so restarts do not ask again) and when a script starts; outdated ones are warned once in the console and listed on the admin dashboard. Panel: General, Updates (`updates.check`, `updates.ignore`). Unauthenticated GitHub allows 60 requests an hour per server IP.
- Script recommendations (owner decision: free scripts worth installing; `resource/server/recommendations/`): each entry in `RECOMMENDATIONS` (`index.ts`) has an id (the product's resource name), title and one-line why (ai-core lang keys `ADMIN_REC_<NAME>` / `_DESC`), the product url, `free` (the dashboard shows a "Free" chip) and `shows(runs)`, its condition (`runs(resource)` = started and not stopping; tgiann-phone: no phone in ai-core's phone layer, `phones.active === null`; tgiann-esc-map: that resource does not run). Adding one = one entry plus its two lang keys; a condition on another ai-core layer uses that layer's picker (`onSwitch` re-checks). Conditions are re-checked on resource start / stop, phone layer switches and settings changes (no polling); the shown ones go into the admin open answer (`AdminOpenData.recommendations`) and to admins with the panel open as `RecommendationDelta` (`ai-core:admin:recommendation`, NUI `adminRecommendation`), and are printed once in the console 15 s after start (`ADMIN_REC_CONSOLE`). The owner dismisses one with the card's X (settings `recommendations.dismissed`, ids; the card hides at once from the panel's own settings copy) and brings it back by removing the id in General, Recommendations. Web: `features/admin/Recommendations.tsx` (dashboard section under Updates) and `recommendationActions.ts` (open snapshot, deltas, dismiss; "Open page" calls FiveM's `invokeNative("openUrl", url)` in game, a new tab in the browser preview). The schema section and card live in `recommendations/schema.ts` because the web preview imports the panel schema (no FiveM code there).
- Setup guide (owner decision): while ai-core's `setupDone` setting is off, every player who spawns gets a welcome card (`resource/server/setup.ts`, `client/setup.ts`): admins open the panel from it, which starts on the setup guide (web `Setup.tsx`); others see the `add_principal identifier.fivem:<id> group.admin` line to copy into permission.cfg. The guide's last step turns `setupDone` on.
- Connecting goes through one gate (`resource/server/connection/`): ai-core's checks (a FiveM account; no unneeded script running next to its replacement, panel switch `refuseOnConflict`) and the checks other resources add with `AddConnectionCheck`. Unneeded scripts (owner decision: a server owner who installs tgiann-inventory is told to delete ai-inventory) come from built-in rules (ai-* stand-ins; every third-party adapter of a layer with an ai-* default: inventory, clothing, keys, dispatch, death, prison, weather, fuel, door locks, garages, plus the radial and HUD names in `CLIENT_LAYERS`; an adapter marked `besideOurs` runs next to the ai-* one on purpose, owner decision), `ai_replaces '<resource>'` lines in any fxmanifest and `RegisterReplacement`; the console names the folder to delete, and while both run nobody can join.
- The ESX/QB/Qbox bridge is part of ai-core (owner decision): it `provide`s `es_extended`, `qb-core` and `qbx_core` and answers their exports, core objects and events from Lua files in `bridge/`, so other scripts use ai-core as their framework (`.claude/rules/lua-bridges.md`, `docs/compat/README.md`).
- Every ai-* resource logs through ai-core (`Log` export, lib `aiLog`), like tgiann-core: resources name channels, ai-core sends to the providers its panel turns on (`data/logs.json`: console, Discord, Fivemanage, FiveM Stats; minimum level, ip on/off). Webhook urls and the Fivemanage key are panel-edited too, but in `data/secrets.json` (git-ignored: `discordWebhooks` by `<resource>/<channel>`, `<resource>` or `default`, `fivemanageKey`); env.cfg is not used for them (owner decision). ai-core logs its own events (characters, money, jobs, gangs, client errors) from its local events in `logs/coreEvents.ts`.

## Contracts

- Exports: typed in `@aicore-fivem/shared` `exports.ts` (`AiCoreServerExports`, `AiCoreClientExports`), registered in `resource/server/exports/` (one file per domain) and `client/playerState.ts`.
- Server local events (`CORE.*` in `@aicore-fivem/shared`): `playerLoaded (src, CharacterInfo)`, `playerSpawned (src, charId)` (the spawn went out: after `playerLoaded`, after the pick with `spawn.choose`), `playerUnloaded (src, charId, "dropped" | "switch")`, `moneyChanged (src, account, balance, delta, reason)`, `jobsChanged`, `dutyChanged`, `gangsChanged`, `activeGangChanged`, `characterDeleted (charId, userId)` (any soft delete: character screen, Players section, `DeleteCharacter`; a delete through the framework projections at that account's next projection refresh: load, create or leave), `playerDied (src, killer, weaponHash, DeathInfo)` (`player/deaths.ts`: FXServer's `onPedDeath` with who / how / where worked out from the server's entities and the weapon hash; the driver of a vehicle that ran the player over counts as the killer; never from a client). Client: `client:playerLoaded (AiPlayerData)`, `client:playerUnloaded`.
- Player data channel to the owner's client: snapshot at load, then `(key, value)` deltas; `money` and `metadata` travel as patches of the changed entries only (`PLAYER_DATA_PATCH_EVENT`); `job` is the current job (on duty, else last on duty, else the first, else unemployed), sent again whenever duty or memberships change. Client side: lib `onPlayerData` / `getPlayerData`, `GetPlayerData` export for late starters. Server local events `metaChanged (src, key, value)` and `definitionsChanged (file, name)` (a panel edit of a job or gang, or a script's definition registered / removed).
- GlobalState `ai:duty:<job>`: on-duty count per job; `ai:inventory` / `ai:vehicleKeys` / `ai:appearance`: the active inventory's, key system's and clothing script's resource names (client adapter pick).
- Connection and conflict exports: `AddConnectionCheck(id, (source, identifiers) => reason | null)`, `RegisterReplacement(remove, keep?)` (keep defaults to the caller), `GetConflicts()`.
- Bans (`resource/server/bans/`, table `ai_core_bans`, lib `bans`): exports `BanPlayer(source | { identifiers }, reason, minutes?, by?, done?)` (true = holds at once, matching online players dropped; `done(banId | null)` after the insert), `UnbanPlayer(banId, by?)`, `IsBanned(source | { identifiers })`, `GetBans(page)` (active, newest first, 50 a page), `GetBanHistory(target, done)` (every ban of the target's identifiers in any state, `BanRecord[]`, newest first, at most 100), `ListBans(BanQuery, done)` (`BanListPage`: filter active / expired / revoked / all, search, keyset `cursor`), `EditBan(banId, { reason?, minutes? }, by?)` (an active ban's reason and / or end from now, null = permanent). Identifiers `fivem` / `license` / `discord` / `ip` without the `type:` prefix. Active bans load once at start into a `BanStore` (sets per `type:value`, plus an id-sorted array for the active list's keyset pages); the gate's `ai-core:bans` check reads only memory (refusal `BAN_REFUSED` with reason, end and id; `BAN_STARTING` until the list is read; a failed read lets everyone in and logs). Every ban, change and lift reaches admins with a ban screen open as a `put` delta from the mutator (`bans/watchers.ts`); reads and keys in `bans/query.ts`, admin screens `resource/server/admin/CLAUDE.md`. Times are written as JS dates (node local, the engine reads them back the same way). Logged on channel `bans` with the admin as source.
- Characters by id, loaded or not (`resource/server/characters/`, lib `characters`): `SearchCharacters(text, done, cursor?)` (`CharacterSearchPage`, the admin search's rules and indexes, `characters/search.ts`), `GetOfflineCharacter(charId, done)` (`OfflineCharacter`: info, money by account type, jobs, gangs, active gang, metadata, position, `lastSeen`, `source`), `GetCharactersOfUser(userId | license, done)`, `GetJobMembers` / `GetGangMembers(name, done, after?, limit?)` (`MembersPage`, keyset by character id, index `job (job, char_id, grade)` / `gang (...)`, added to old databases by `admin/players/indexes.ts`), `Add` / `Remove` / `SetOfflineMoney(charId, account, amount, reason?, done?)`, `SetOfflineJob` / `RemoveOfflineJob`, `SetOfflineGang` / `RemoveOfflineGang`, `SetOfflineMeta`, `SetCharacterInfo(charId, patch, done?)`, `DeleteCharacter(charId, by?, done?)`; writes answer `{ ok }` or `{ ok: false, error: <lang key> }` (`CharacterResult`). `characters/edit.ts` runs them one at a time per character: a loaded character changes through its `Player` (same as the source exports), a stored one waits until no load, unload save or admin edit holds it, then changes while `claims` holds it (it cannot load meanwhile) through the Players section's offline mutators (`admin/players/offline.ts`: money through `Account` and the money writer with its ledger row, after draining the writer, answering the batch's real outcome (`moneyWriter.commit()`; a rolled-back batch answers `ADMIN_PLAYERS_ERR_WRITE` and tells no watcher); memberships under `maxJobs` / `maxGangs`, the multi-off replace in one transaction). `DeleteCharacter` refuses a loaded character (`ADMIN_PLAYERS_ERR_ONLINE`: kick or switch it first); `SetCharacterInfo` changes the sex only while not loaded.
- Script job / gang definitions (`resource/server/jobs/runtime.ts`, lib `definitions.registerJob` / `registerGang`): `RegisterJobDefinition(name, def)` / `RemoveJobDefinition(name)` (+ gang twins) put the definition into the same maps as the panel's, owned by the caller (`ByResource`, gone when it stops), never into `data/*.json`; a panel name wins (`CORE_ERR_DEFINITION_PANEL`; a panel record made later takes the name over), another resource's name is refused (`CORE_ERR_DEFINITION_OWNER`). Clients get them as GlobalState `ai:jobdef:<name>` / `ai:gangdef:<name>` (cleared at ai-core start); `client/definitions.ts` merges them under the panel files in `GetDefinitions` and `CORE.clientDefinitionsEvent`.
- Player extras (`resource/server/player/extras.ts`, lib `characters`): `SetPaycheckEnabled(source, on)` / `IsPaycheckEnabled` (runtime flag on the `Player`, the paycheck skips it; every load starts paid), `GetPlayTime(source | { charId }, done?)` (metadata `playtime`, seconds, added at each save, plus the running session), `SavePlayer(source, done?)` (the periodic save for one player now, then its queued writes).
- Vehicle key exports `GiveVehicleKeys`, `RemoveVehicleKeys`, `HasVehicleKeys` (source, entity or plate), typed `VehicleKeysServerExports`; server -> client `ai-core:client:vehicleKeys (action, netId, plate)` for client-API-only systems. Client `HasVehicleKeys(entity | plate)` (`VehicleKeysClientExports`, `client/vehicleKeys/has.ts`, lib client `vehicleKeys.has`) answers from a per-plate mirror of the server layer's answers (10 s): filled by `VEHICLE_KEYS_HAS_CALLBACK (netId | plate)` when the player enters a vehicle or asks about an unknown / stale plate (that call answers false or the old value), and by `VEHICLE_KEY_HELD_EVENT (plate, held)` to the player after each give / remove through the layer. Key systems keep no client state ai-core could read, so a key a system grants itself (lockpick, hand over) shows after the mirror expires.
- Inventory exports (server `AddItem`, `RemoveItem`, `GetItemCount`, `HasItem`, `CanCarryItem`, `GetItems`, `ClearInventory`, `RegisterStash`, `OpenInventory`, `RegisterUsableItem`, `GetItemDefinition(s)`, `GetInventoryWeight` (a player's weight and limit in grams, null when the inventory does not tell), `SetItemMetadata(inv, slot, metadata)` (replaces a stack's metadata), `SetMaxWeight(source, grams)` (until the inventory reloads it), `GetUsableItems()`, bridge-only `UseItem` / `IsUsableItem`; client `OpenInventory`, `HasItem`, `GetItemCount(item)` (the inventory's own client count, null without one), `GetItems()` (the local player's stacks from the inventory's client list, null without one) and local event `CLIENT_ITEM_COUNT_EVENT (item, count, previous)` after each change of a total (`resource/client/inventory/index.ts`), `GetItemDefinition(s)`, `GetCurrentWeapon` (the held weapon item, `HeldWeapon`)), typed `InventoryServerExports` / `InventoryClientExports`; local events `inventoryChanged (resource | null)`, `itemUsed (src, name, status | null)`.
- Item definitions on every client (`server/inventory/clientDefinitions.ts`, `client/inventory/definitions.ts`): each client asks once at start (`ITEM_DEFINITIONS_CALLBACK`), then the server broadcasts only changed definitions (`ITEM_DEFINITIONS_EVENT (Record<name, def | null>)`), worked out by reading the active inventory's definitions again and diffing against the last sent JSON when an inventory becomes active (a restart of the same one sends nothing) or its adapter emits `ITEM_DEFINITIONS_CHANGED_EVENT` (ai-inventory on an item panel edit, its local `ai-inventory:itemsChanged`); while none runs the last definitions stay. The client re-emits each applied change as local `CLIENT_ITEM_DEFINITIONS_EVENT` (the snapshot as one change of every item) for the bridge.
- The shared player UI (notifications, progress bar, prompts and the interaction key, menus, input dialogs, minigames, server-run bars) is ai-lib's (`resources/[ai]/ai-lib/CLAUDE.md`); the bridge's framework UI and ai-core's own scripts (spawn chooser) use it through the lib.
- Export `GetUpdates()`: the outdated scripts (`UpdateInfo`).
- Exports `GetUserId(src)` (account id, also on the character screen) and `GetCharacterInfo(charId, done)` (a character loaded or not with its `userId`; stored ones cached 5 min, `characters/info.ts`).
- Dispatch export `SendDispatchAlert(alert) -> boolean` (`DispatchAlert` in `@aicore-fivem/shared` `dispatch.ts`, lib `dispatch`); ai-core answers `police:server:policeAlert` (client `(text)`, server `(text, camId, playerSource)`).

- Ledger export `GetAccountHistory(LedgerRef, done, { before?, since?, limit? })` (`LedgerPage`, read only, keyset on `account_time`, `money/history.ts`; lib `money.history`).

## Pitfalls

- `ai_core_accounts.owner_id` is text: compare with `CAST(id AS CHAR) COLLATE utf8mb4_unicode_ci` in joins. Without the cast the unique key is not used; without the COLLATE the cast takes the connection's `utf8mb4_general_ci` and MariaDB refuses the comparison ("Illegal mix of collations").
- `mysql.transaction` answers `false` on rollback without throwing; the money writer logs it and answers it only to `commit()` (live changes stay synchronous and never learn it: their memory is already the truth).
- An unloading character stays claimed until its save, its membership queue and its money batch are in the DB (`unloadCharacter`), so a stored-character write or load right after never runs before them; it waits with `moneyWriter.settled()` (the batch's own timer), not `idle()` (one early transaction per drop).
- The dev commands answer in the server console (`print`), not in ai-chat (only `addCommand`'s own errors are notifications); the system chat is off (`resources_useSystemChat false`) because ai-chat provides `chat`.
